# ILCE-7CM2 服务模式预加载机制研究

[English](README.md)

本仓库记录 ILCE-7CM2 官方 2.01 固件中，从 USB 服务会话到一次性 root 指令执行的路径。认证协议与执行链分开说明，便于核对每一步的作用。

## 指令执行链

1. 相机先以 USB 海量存储设备（`054C:0E8A`）出现。主机打开接口 0、启动 Senser，并完成三轮挑战—应答认证。
2. 相机重新枚举为 `054C:0336`。主机对新的服务设备再次完成 Senser 认证。[协议说明](PROTOCOL.zh-CN.md)列出控制请求、认证帧、摘要输入、返回值及两次认证的顺序。
3. Jiritsu 文件指令选择含 `/tmp/jiritsu/../..` 的路径。在研究的固件上，路径解析会越过预期的 Jiritsu 目录。共享对象被放入临时 Work 存储区；写入预加载配置后，服务接口从 `/etc/ld.so.preload` 回读到了该对象路径。
4. Jiritsu DEBUG 请求为固定系统命令启动一个 root 子进程。其动态加载器读取 `/etc/ld.so.preload`，装入共享对象，并在固定命令运行前执行对象的初始化函数。
5. 工作对象写出带版本的结果记录并删除预加载条目。主机分别回读结果和预加载路径，再确认 USB 回到普通设备身份。

```mermaid
flowchart LR
    A[0E8A 海量存储] --> B[Senser 认证]
    B --> C[0336 服务认证]
    C --> D[Jiritsu 路径解析]
    D --> E[预加载配置]
    E --> F[DEBUG root 子进程]
    F --> G[共享对象初始化代码]
```

信任边界在两处连续被跨越：路径解析离开 Jiritsu 预期目录，随后特权子进程读取了服务接口可控制的预加载文件。USB 服务访问是入口；动态加载器使文件控制变成指令执行。带版本的结果记录，比仅看到 USB 传输成功或模式切换更能证明执行发生。

## 能做什么

已观察到的是子进程内的临时代码执行。它可用于检查内部状态，或访问该进程权限允许的数据。固件制作是独立的离线任务；要安装修改后的固件，还需要更新接受路径。预加载执行不会永久关闭签名检查。已研究的更新流程在结束后恢复了临时门控。

本文结论针对 ILCE-7CM2 官方 2.01。其它版本应分别检查 USB 会话、Jiritsu 路径、加载器和子进程权限。认证帧的公开参考实现见 [Sony-PMCA-RE Senser 源码](https://github.com/ma1co/Sony-PMCA-RE/blob/master/pmca/usb/sony.py)。
